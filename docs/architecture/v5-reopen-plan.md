### 2.2 逐方案展开

#### P1 · 主模型先给 3–5 候选 + Jev 候选内排序/确认

- **做法**：`commander_task_dispatch` 或新工具先让指挥官（主模型）基于对话上下文写 3–5 个候选（工作区×会话模式）；Host 用 Jev 在候选内做 choice（3–5 路）或 noul 排序 + 门控；仍返回 `needs_confirmation` 时走确认卡。
- **优点**：候选内 choice 难度大幅下降（概率分布不再被 28 路稀释）；模型最了解对话意图，适合处理 c；实现改动集中（候选构造 + 一次 Jev 调用）。
- **缺点/风险**：**模型先选 = 把"选目标"的主权从 Jev 移到主模型** → 触碰冻结决策 6（"Jev 只判工作区/会话"、不做 Top-K 预筛）与 PRODUCT-DESIGN D3/D4（Jev 独立判定 + 门控）；需要用户批准产品语义变更。模型候选若错，Jev 只能"在错的集合里选"。
- **成本**：中（1 次模型调用 + 1 次 Jev；Host/工具 schema 改动；确认卡不变）。
- **需要证据才能选**：① P1 原型在 v3 案例上模拟（用主模型离线产候选，不接 live Jev）→ 候选集包含正确目标的召回率 ≥ 某一门槛（如 ≥95%）；② 候选内 Jev 排序 top-1 准确率；③ 对比 P2 的准确率/成本。

#### P2 · Jev 逐候选 noul 打分排序（能力面板同款）

- **做法**：对每个候选工作区生成一条"这个工作区是否适合该任务"的 noul question（或逐候选一次调用），取 score 最高者；会话同理。门控改用 score（0–1）与人工阈值，不再依赖 choice 的 probabilities/confidence。
- **优点**：不改变"Jev 判定"的产品语义，只改问法与打分；能力面板已验证 noul 在 150+ 能力上可用（`capability-panel-api.md`）；score 可用于排序 + abstention（比 confidence 稳）。
- **缺点/风险**：请求体积与耗时上升（28 条 noul vs 1 条 choice；需实测 token/时延）；Jev 对"工作区级别"的 noul 判据是否有效**未验证**；同质工作区仍会共同高分（b 不解决）。
- **成本**：中（Jev 请求构造 + 解析 + 门控；ARCHITECTURE §5.3/§5.4 需更新为 noul 口径——改实现契约，不改冻结决策 6 的"Jev 判定/全量候选"语义）。
- **需要证据**：① noul 版在 v3 案例的 workspace Top-1（对比 v2 的 14.3%）；② 单案 token/时延（B 模式是否仍 ≤24k/请求、p95 <3s）；③ noul score 的分桶区分度（替代 f）。

#### P3 · 分层：模型按上下文写 brief/候选，Jev 只做置信与 tie-break

- **做法**：明确分工——主模型负责"把对话意图写成 brief + 初选 1–3 个目标"，Jev 负责"给候选打分/置信 + 冲突时 tie-break + 低分触发确认"；Host 不再用 Jev 做 28 路首发选择。
- **优点**：直接针对 c（无 brief）与 a（28 路）；产品体验上更接近"指挥官真的在指挥"。
- **缺点/风险**：**明确改变产品语义**（PRODUCT-DESIGN D3"Jev 独立判定 + 门控"→ Jev 降为辅助；冻结决策 6 的"Jev 只判工作区/会话"被扩展为"模型先判、Jev 复核"）→ 必须用户批准；模型幻觉/越权风险上升（误选、漏判）；评估要新增"模型候选质量"指标。
- **成本**：中–高（prompt/工具契约/确认卡/评估口径均动）。
- **需要证据**：① 主模型在 v3 案例上的"候选质量"（top-1/top-3 命中）；② Jev 复核是否真的能降低错误（对比"仅模型"vs"模型+Jev"）；③ 用户对"模型先选"的产品接受度（这是产品决策，不是数据能替代的）。

#### P4 · 缩小派发范围（白名单 3–8 工作区）+ 会话只问该工作区

- **做法**：M1 默认要求用户配置 `allowedWorkspaces`（3–8）；Jev 只在这个集合内 choice；会话问题沿用 B 模式第二问。
- **优点**：改动最小（主要是产品默认值与设置页，机制已在设计里）；成本/时延下降；同质项可能被用户排除。
- **缺点/风险**：v2 实测"前 8 活跃"白名单 Top-1 只到 26.9%（且模式更差 34.6%）→ **单靠 P4 不解决精度**；白名单收窄 = 产品可用性下降（用户没配置时无法派发）。
- **成本**：低（配置/默认值/提示）。
- **需要证据**：① 用户在真实使用中愿意配置的白名单规模；② P4 单独/与 P1/P2 组合下的 Top-1；③ 期望工作区不在白名单时的 `needs_confirmation` 比例（v2 为 5/50）。

#### P5 · 每次确认（保底）

- **做法**：即当前 `NEXT-PHASE §7.3` 降级：`commander_task_dispatch` 永远返回 `needs_confirmation`；Jev 只给建议不门控放行；用户每次确认。
- **优点**：零精度风险（人兜底）；立即可用；不改冻结决策（§7.3 已授权）。
- **缺点/风险**：产品体验（每次点确认）与"低置信才问人"的卖点后退；V5 永不通过（除非部分确认场景另算）。
- **成本**：低（当前蓝图已写 `autoDispatch=false` 路径）。
- **需要证据**：无需额外证据；只需用户接受产品语义。

### 2.3 方案选择矩阵（证据 → 倾向；最终由 lead/用户定）

|---|---|---|

## 3. V5 重开门（数据集 v3）评估协议

> 命名澄清：这里的 "v3" 指**数据集/评估轮次 v3**，不是 V0 验证阶段的 V3（sessionController）。本协议只改"输入与评估轮次"，**不改任何指标阈值**。

### 3.1 数据与冻结（沿用 §6.2A/§6.2B）

1. **按被测消息时间重冻结**：`dispatchAt = 被测用户消息时间`（修 v2 的 12/50 偏差）；在冻结前验证 `dispatchAt == messageTime` 全 50 条。
2. 新副本：`docs/eval/frozen/cases.real.v3.<sha12>.jsonl` + `manifest.v3.json`（sha/generator 双哈希/seed/summaryMode/dispatchTime/layerCounts/leakViolations）。**不得覆盖 v2 副本**（`872cb12d…` 永久只读）。
3. **A1–A12 全过**：audit-cases violations=0（A4 按可执行细则；A12 校验 dispatchAt 偏差为 0 + 报告披露）。
4. **38/50 标签人工复核**：产出 `labels.v3.reviewed.md`（逐条：期望工作区/accept-set、mode、会话、是否应询问、复核人）；should-ask 5 条全部重判；`needsReview=0` 或剩余有 lead 签字豁免。
5. **口径沿用**：named-cue 单列、C2=non-named-cue n、C6=门禁层 labeled(45)；能力提及层仍为观测项。

### 3.2 新增「可推断子集」分层（只作诊断口径，不替代门禁）

- **定义**（建议，待 lead 批准）：任务文本**自包含**（不依赖会话上下文即可理解目标）、且期望目标在快照中**唯一可推断**（工作区职责/会话标题与任务语义有明确指向；人工复核判定）的样本。
- 目的：把"输入可推断性"与"判定架构能力"分开看；避免把 c 的输入缺陷算成算法失败。
- 报告要求：`inferable` 子集与 `all` 同时给 C2/C4（门禁仍按 `all` 口径，除非 lead 批准改为 `inferable`——**这是口径变更，需单独裁定**）。

### 3.3 样本量

- **same 50 例**：保证与 v2 可比（同案例、同标签规则、仅修 dispatchAt/标签复核）。
- **新增自包含样本**：建议 +20–30 条（从真实历史里选"首条即自包含"、"任务文本含明确领域/对象"的会话消息，人工确认），用于检验"输入变好时架构是否跟得上"；新增样本进 v3 门禁前需 lead 批准样本量变更（避免"换数据集刷分"）。
- 总数建议 70–80 条，仍按六层+观测层分布（比例沿用或按新增样本微调，变更需批准）。
