# 多轮任务详情 · 逐项材料（方案 B）

> 日期：2026-11-20
> 对比对象：`prototype/task-detail-materials/`（方案 A · 报告级材料）
> 目标：把材料直接挂到每条验收项下面，验证「逐项材料表」在 440px 面板里的信息密度和可读性。
> 状态：静态设计稿；截图里的配置/对比图是本地 mock 素材。

---

## 打开

```bash
python3 -m http.server 4311 -d prototype/task-detail-materials-per-item
# http://127.0.0.1:4311/
```

| 参数 | 取值 | 说明 |
|---|---|---|
| `solo` | `1` | 只显示详情面板（窄窗截图） |
| `expand` | `1` | 展开第 1 轮 |
| `compose` | `1` | 打开继续派发 composer |
| `theme` | `dark` / `light` | 主题 |
| `focus` | `materials` | 滚到验收区 |
| `materials` | `all` | 展开所有验收项的材料表 |
| `lightbox` | `1` | 直接打开图片预览 |
| `sheet` | `1` | 直接打开文件动作单 |

底部设计稿控件：`默认` / `展开第 1 轮` / `材料全展开` / `查看大图` / `继续派发` / `浅色`。
快捷键：`1` 默认、`2` 展开第 1 轮、`3` 继续派发、`4` 材料全展开、`5` 查看大图、`T` 主题。

## 和方案 A 的差别

| 位置 | 方案 A（报告级） | 方案 B（逐项） |
|---|---|---|
| 结论下方 | 一个「依据与材料」大块，图片 2 列 + 链接/文档列表 | 不再有报告级材料块；结论底部只写 `2 条验收 · 7 份材料` + `查看验收` |
| 验收项 | 只有证据文本 + 1–2 个材料 chips | 每条验收项自带一个可折叠的「材料 N」表 |
| 图片 | 2 列大缩略图，视觉优先 | 52×34 小缩略图，跟在验收项后面 |
| 链接/文档 | 报告级统一列表 | 分到各验收项下，各自成表 |
| 无归属材料 | 有地方放（报告级） | 必须归到某条验收项，或没有位置 |

## 方案 B 的结构

```
整理报告
├── 结论
│   └── 2 条验收 · 7 份材料   [查看验收]
└── 验收 2 条                     7 份材料
    ├── ✓ 核对 Htdot 依赖的模型版本…   [材料 4 收起]
    │     证据 · Htdot 配置 · 模型别名清单
    │     [缩略图] 订单中心模型配置 · PNG
    │     [xlsx] Htdot 模型依赖清单.xlsx
    │     [link] 官方发布记录 · docs.z.ai
    │     [link] HuggingFace · zai-org
    └── ✓ 给出升级/不升级建议…          [材料 3 收起]
          证据 · 兼容性结论 · 回滚开关
          [缩略图] SKU 边界对比 · PNG
          [pdf] GLM 兼容性评估.pdf
          [link] BigModel 在架模型列表
```

- 每条验收项是一个 `item-check`，标题、证据、材料数量都在一行；右上角 `材料 N` 是折叠按钮。
- 材料表缩进在验收文本下方，用虚线分隔；图片是行内小缩略图，点击打开大图；文档/链接行沿用统一动作。
- 验收区顶部只保留一个总览：`验收 2 条 · 2/2 有证据 · 7 份材料`，不再重复报告级材料。

## 适合 / 不适合

**适合**

- 验收项和材料是一一对应、边界清楚的场景；
- 用户会逐条验收，希望「点开这一条就能看到它的证据」；
- 材料数量少（每条 1–3 个），且很少跨项复用。

**不适合**

- 同一份材料支撑多条验收（官方发布记录、设计稿、总报告）——方案 B 要么重复展示，要么强行归到一条；
- 存在「不属于任何验收项」的背景来源（渠道列表、方法论说明）；
- 验收项很多（6–10 条），每项再带 3–4 个材料，页面会非常长；
- 用户想先扫一遍所有图片——方案 B 的缩略图太小，视觉证据被切成碎片。

## 数据/契约含义

如果采用方案 B，存储仍建议只存一份材料，用 `acceptanceId` / `acceptanceIds` 关联，而不是每条验收项各存一份：

```ts
interface ReportMaterial {
  id: string
  kind: 'link' | 'file' | 'image'
  title: string
  url?: string
  path?: string
  source: 'presented' | 'commander' | 'session'
  acceptanceIds?: string[]   // 方案 B 的核心字段
  // ...
}
```

- 一个 material 可以挂多条验收项，UI 在每个 item 下重复渲染同一 id；
- 没有任何 `acceptanceIds` 的材料需要一个「补充来源」落点，否则会被丢掉；
- 方案 B 的排序/分组逻辑在客户端：先按验收项，再按材料类型；Host 仍返回扁平 `reportMaterials[]`；
- 如果 Host 直接派生 `acceptance[].materials[]`，要注意同一材料在多条验收项下的去重与编辑（改标题要同步所有副本）。
