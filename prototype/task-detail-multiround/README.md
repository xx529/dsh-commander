# 多轮任务详情 · 页面设计

> 日期：2026-11-19
> 对应需求：任务详情与时间线要支持**多轮追加派发**；顶部以标题为主；派发内容收进时间线，并且同时出现**用户原话**与**工作会话实际收到的派发文本**。
> 配套契约草案：`docs/architecture/m5-continue-dispatch.md`

---

## 打开

```bash
python3 -m http.server 4311 -d prototype/task-detail-multiround
# http://127.0.0.1:4311/
```

也可以直接双击 `index.html`（纯静态、无构建、无外部依赖）。

| 参数 | 取值 | 说明 |
|---|---|---|
| `expand` | `1` | 展开第 1 轮 + 所有派发原文（看完整派发内容） |
| `compose` | `1` | 打开「继续派发」composer |
| `theme` | `dark` / `light` | 主题 |
| `solo` | `1` | 只显示详情面板（去掉背景看板），用于窄窗/整页截图 |
| `full` | `1` | 面板随内容增高、不内部滚动；配合 `solo=1` 截整页 |

底部「设计稿」浮条：

- `默认`：第 1 轮折叠、第 2 轮展开；
- `展开第 1 轮`：显示用户原话 + 派发原文；
- `继续派发`：打开 composer；
- `浅色`：切换主题。

快捷键：`1` 默认、`2` 展开第 1 轮、`3` 继续派发、`T` 主题。

---

## 要解决的问题

现在的详情（方案 D）是「一条编年时间线 + 结构化卡片」：创建 → 派发回执 → 会话 → 整理报告/验收。单轮任务够用，但多轮时有三个语义缺口：

1. **派发回执只有 Jev/目标，没有真正发出去的文本**。用户看不到工作会话到底收到了什么，也就无法判断这一轮的要求是否准确。
2. **没有用户原话**。时间线里只有「派发」这个动作，没有触发这次派发的原话（聊天里说的，或看板上继续派发写的批注）。
3. **轮次边界不清晰**。第 1 轮的验收、第 2 轮的派发和验收混在一条线上；任务级进度条（待派发/进行中/待验收/已完成）无法表达「第几轮、发到哪个工作区」。

另外，顶部第一行现在是「状态 · 工作区 · 优先级」，标题在第二行；窄窗（原生壳 506px）里标题不够第一眼。

---

## 设计决策

### 1. 顶部标题优先

- 第一行就是任务标题；状态/工作区/优先级/轮次/更新时间全部下移到标题下的 meta 行。
- 删除任务级四段进度条（待派发/进行中/待验收/已完成）。它已被看板列和轮次导航取代；保留会让「第 2 轮」和任务状态打架。
- 标题沿用现有「点进编辑」能力；右上角只留「更多 / 关闭」。
- 目标默认 2 行，可展开；不抢标题。

### 2. 轮次编年，而不是单线混排

- 每个轮次是一个 section：`第 N 轮 · 目标工作区/会话 · 时间范围 · 验收数`。**轮次不带状态**——完成/待验收/进行中只属于整个任务；当前轮在顶部轮次导航里用「当前」标记。
- 当前轮展开；历史轮默认折叠成一条摘要，摘要里保留**用户原话的首句**和本轮结果（`6/6 验收通过`），点开才显示完整时间线。
- 顶部有轮次导航（`第 1 轮` → `第 2 轮`，`共 N 轮`），可以直接跳到某一轮。
- 轮次内的叙事顺序固定为：
  **用户原话 → 派发（含 brief）→ 工作会话 → 整理报告 → 验收**。
- 「现在」只出现在当前轮末尾，提示下一步动作（等待验收 / 正在执行 / 可以继续派发）。

### 3. 用户原话是一等公民

- 每条轮次开头有一个「用户原话」块：
  - 来源标签区分 `指挥官会话`（聊天里说的）和 `看板 · 继续派发`（返工批注）；
  - 原文完整展示，不总结；长文本可换行；
  - 历史轮折叠时，摘要里保留一句原话预览。
- 这样「为什么会有这一轮」永远可追溯，不依赖指挥官自己的归纳。

### 4. 派发内容是时间线的一等公民

- 「派发」事件 = 目标行 + **派发内容卡**：
  - 目标：`工作区 · 新建会话 / 原会话 / 自定义`；
  - 正文：「工作会话收到的原文」，即 `buildDispatchBrief` 实际发出的任务/目标/本轮要求/上一轮结论/约束；
  - 默认折叠 4–5 行，`展开全文` 看完整文本；
  - Jev 置信度、采用建议/自定义、候选数、确认时间降级为卡底的一行 `details`，不再占据卡片主位。
- 新一轮的 brief 会把「本轮要求」「上一轮结论」「上一轮验收项」显式写出来，设计上原样展示——这正是多轮语义。

### 5. 工作会话与验收按轮归属

- 会话卡显示 `工作区 · 会话标题 · 第 N 轮`，打开会话仍是主动作。
- 报告/验收块只属于当前轮；历史轮折叠时只显示验收数，展开后看完整验收。
- 历史验收不再和当前验收混在一个列表里（对应契约里的 `acceptanceHistory`）。

### 6. 看板卡片显示轮次，不显示验收 N/N

- 看板卡只回答「第几轮、哪个工作区、什么时候」；多轮任务用 `第 2 轮` / `第 1 轮` 徽标区分。
- `验收 N/N` 在 review 状态下恒等于满分，信息量为零，且会让人误以为它是任务级状态；验收数留在详情页的「验收」区。
- 轮次徽标对 `round=1` 用中性色，`round>1` 用品牌色，避免所有卡片都高亮。

### 7. 继续派发的语义在页面上说清楚

- review 状态的底部操作：`继续派发` / `通过验收`。
- 点「继续派发」打开 composer：
  - 标题明确「第 N+1 轮」；
  - 提示「任务保持待验收，指挥官确认后才会真正派发」；
  - 目标二选一：`原会话` 或 `新工作区 / 新会话`（最终目标仍由确认卡决定）；
  - 提交后只通知指挥官，不直接改任务状态。
- 这样和「返工 = 给指挥官一条任务更新信息，由指挥官统一再次派发」的产品口径一致。

## 数据与契约要求

页面本身是静态原型，但下面这些字段/接口是落回生产客户端时必须补的（已写入 M5 契约草案）：

| 需求 | 字段/接口 | 说明 |
|---|---|---|
| 每轮的用户原话 | `DispatchRecord.userRequest?: { text; at; source: 'chat'\|'board' }` | 由 `dispatch_task.userRequest` 显式传入；看板继续派发用 `pendingInstruction`；旧记录缺失时显示「未记录原话」 |
| 每轮实际派发文本 | `DispatchRecord.brief: string` | `spawnDispatch` 已经生成 brief，但目前只返回未落库；`finishDispatch` 要写入 dispatch 记录 |
| 多轮派发记录 | `GET /commander/tasks/:id` 增加 `dispatches[]` | 现在只返回 `task.dispatchId` 对应的**最新**一条；渲染每轮必须拿到全部 |
| 轮次边界 | `TaskRecord.round` / `acceptanceHistory` / `SessionLinkRecord.round` | 见 M5 契约 §4；客户端按轮分组；`round` 只是序号，不承载任务状态 |
| 当前轮验收 | 现有 `acceptance`（只存当前轮） | 历史轮用 `acceptanceHistory`，不参与 review 门禁 |
| 报告结论按轮 | `reportSummary.round` 或 history 里的 summary | 每轮结论只挂在对应轮次 |

推荐 Host 直接派生一个只读的 `rounds[]` 返回（每轮含 `userRequest / dispatch / sessions / report / acceptance`），客户端不再自己 join `timeline + dispatches + sessions`；如果不想加派生层，用 `dispatches[] + timeline[].round + sessions[].round` 也能组合，但两边会重复分组逻辑。

**旧数据降级**：没有 `brief`/`userRequest` 的记录，派发卡显示「旧记录未保存派发原文」，用户原话块回退到任务 goal 或隐藏；不要用当前 goal 冒充历史原文。

## 与现有实现的关系

- 现有生产详情在 `packages/dsh-commander/src/client/BoardPage.tsx` + `board.ts` 的 `buildTaskFeed`；本设计是它的多轮版本，不是从零的新页面。
- 现有 `prototype/task-detail/` 的 D 方案（编年审阅）是本设计的基础；本设计只改三件事：
  1. 头部顺序：标题第一；
  2. 时间线按轮分组，补「用户原话」和「派发原文」；
  3. 底部继续派发 composer 的语义。
- 原生壳（506px）下同样适用：面板宽度自适应，`@media (max-width:720px)` 下轮次头会换行、底部操作纵向排列。

## 待确认

1. 历史轮默认折叠（当前设计）还是全部展开？推荐折叠，长任务更可控。
2. 用户原话由指挥官通过 `dispatch_task.userRequest` 显式传入（推荐，可审计），还是 Host 从指挥官会话最近一条用户消息自动抓？自动抓在多轮/多任务下容易错配。
3. 工作会话的原始最后回复是否也要进页面？当前用「指挥官归纳的结论 + 打开会话」；原始回复在会话里，避免详情页变成聊天记录。
4. 标题在窄窗是否限制 2 行？当前不限制，长标题会占 2–3 行；可改为 2 行 + tooltip。
